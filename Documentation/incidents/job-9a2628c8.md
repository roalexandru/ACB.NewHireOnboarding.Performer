## What went wrong

The job was started manually with an explicit input argument, `in_OrchestratorQueueName = "NoSuchQueue_TriageTest"`, a queue that has never existed in this folder. REFramework's stock queue-name-override logic in `Main.xaml` substituted that value in place of the configured queue (`NewHireBenefitsPosting`), so `GetTransactionData.xaml` asked Orchestrator for a queue that doesn't exist, got HTTP 404 twice (retried once), and gave up. Because this project sets `ShouldMarkJobAsFaulted=False`, the framework treated "can't get transaction data" the same as "queue is empty," logged `Process finished due to no more transaction data`, and ended the job green — with the real cause sitting in a `Fatal`-level log line the job state never surfaces.

## Root cause

**Quoted cause** (`references/activity-packages/system-activities/playbooks/queue-transaction-activity-failed.md`, "What can cause it"): *"The queue or storage bucket does not exist in the Orchestrator folder where the job runs, or the robot account lacks permission on it."*

Narrowed to: the queue name resolved at runtime — `NoSuchQueue_TriageTest` — does not exist in folder `CodingAgentsDemos`, and it only reached `GetQueueItem` because the job was launched with that value in the `in_OrchestratorQueueName` input argument, which stock `Main.xaml` (lines 635–655, "If in_OrchestratorQueueName is specified") uses to overwrite `Config("OrchestratorQueueName")` before `Framework/GetTransactionData.xaml` runs. This is documented, unmodified REFramework behavior — `Main.xaml` is on the "Do not modify" list in CLAUDE.md — not a defect introduced by this project.

Surviving upstream question answered: the correctly configured queue (`NewHireBenefitsPosting`, per CLAUDE.md's `Data/Config.xlsx` value) does exist and was never the problem — `uip or queues list` shows it as the only queue in the folder. The failure was caused entirely by the manual job-start override, not by a misconfigured or deleted queue.

## Proposed fix

No `.xaml` change applies — `Main.xaml` and `Framework/GetTransactionData.xaml` are stock REFramework, both marked "Do not modify" in CLAUDE.md, and the override behavior that produced this failure is the framework working exactly as documented. The defect is entirely in how the job was started, which is Orchestrator job-start configuration, not source:

- Don't pass `in_OrchestratorQueueName` when starting `ACB.NewHireOnboarding.Performer` jobs unless intentionally overriding the queue — omit the argument (or pass the empty string) so the process falls back to `Config("OrchestratorQueueName")` = `NewHireBenefitsPosting`, e.g.:
  ```
  uip or jobs start --folder-path "CodingAgentsDemos" <process-key>
  ```
  (no `--input-arguments` / no `in_OrchestratorQueueName` key), rather than whatever manual trigger supplied `{"in_OrchestratorQueueName":"NoSuchQueue_TriageTest"}`.
- Separately (governance, not a fix for this specific job): this project's `ShouldMarkJobAsFaulted=False` setting is why a real Fatal error is invisible in the job's headline `State`. That's an intentional Config.xlsx/robot-level setting per CLAUDE.md, not a defect — flagging it here only because it's the reason this failure needed log-diving instead of showing up as `Faulted`. Any change to it is a `Data/Config.xlsx` value, not `.xaml` source, and is out of scope for this run per the task instructions (no workflow-source edits).
